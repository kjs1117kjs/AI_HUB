SBPORA · TB_WB_LOGIN_HIST / FN_GET_MENU_CHK_YN2

로그인 · 메뉴 IP 차단
운영 가이드

로그인 트리거와 메뉴 접근 함수에 각각 복사돼 있던 차단 규칙을 공용 함수 5개로 합쳤습니다. 이 문서는 그 구조를 설명하고, 계정·IP를 추가하거나 문제가 났을 때 무엇을 어디서 해야 하는지 정리한 운영 문서입니다.

작성 2026.08.26대상 Oracle SBPORA 스키마

1. 무엇이 바뀌었나

이전에는 같은 IP 차단 목록(클라우드 대역 180줄, 개인 계정+IP 쌍, H0268 직원 체크, XFF 추출)이 TR_TB_WB_LOGIN_HIST_R98과 FN_GET_MENU_CHK_YN2에 각각 들어 있어서, 한쪽만 고치면 로그인과 메뉴의 차단 기준이 어긋났습니다.

지금은 규칙이 공용 함수 안의 상수 목록에 한 번만 존재하고, 트리거와 메뉴 함수는 그 함수를 호출해 결과만 받습니다. 대상을 추가할 때 트리거나 메뉴 함수를 열 일은 없습니다.

로그인 시점
TR_TB_WB_LOGIN_HIST_R98

결과가 N이면 이력 INSERT 후 RAISE → 로그인 실패. 임시 차단 쌍은 09~18시에 실제 차단.

메뉴 클릭 시점
FN_GET_MENU_CHK_YN2

결과가 N이면 USE_YN='N'. T면 과호출 카운트 가중과 조회 딜레이만.

4. 대상 관리 — 어디를 고치나

추가하려는 것이 무엇인지에 따라 아래 표에서 한 곳만 고치고, 그 함수만 다시 컴파일합니다.

추가하려는 것파일 / 상수한 줄 형식
감시 대상 계정 하나03 · C_TARGET_USERS'userid'
특정 본사 소속 직원 전체03 · C_TARGET_HQ_CDS'H0268' (TB_HQ_EMPLOYEE.HQ_OFFICE_CD)
특정 매장 소속 직원 전체03 · C_TARGET_STORE_CDS'DS00001' (TB_MS_EMPLOYEE.STORE_CD)

어느 목록에 넣을지 판단

  • "이 계정은 어느 IP로 오든 지켜봐야 한다" → C_TARGET_USERS. 넣는 순간 클라우드 IP 차단, 1분 60회 제한, 접근 이력 INSERT, 특정 화면 2초 딜레이가 모두 적용됩니다.
  • "이 IP 대역은 감시 대상 계정이 쓰면 무조건 막는다" → C_CIDR_LIST. 일반 계정에는 영향 없음.
  • "이 계정이 이 IP로 오면 막는다" → C_HARD_LIST. 감시 대상이 아니어도 동작.
  • "국내 통신사 IP인데 특정 계정만 과하게 접속" → C_TEMP_LIST. 대역에는 절대 넣지 말 것(9절).

예시 — HostRoyale 대역 하나 추가

-- 02_FN_GET_CLOUD_IP_LABEL.sql 의 C_CIDR_LIST 끝에
    ,   '45.10.192.0/21|HostRoyale'
    ,   '203.0.113.0/24|HostRoyale'     -- ← 추가. 형식: 네트워크/프리픽스|라벨
    );

예전처럼 /24를 LIKE '203.0.113.%' 256줄로 풀 필요 없고, /19·/21처럼 옥텟 경계에 안 맞는 대역도 한 줄입니다.

예시 — 계정 + IP 확정 차단 추가

-- 04_FN_CHK_LOGIN_IP_BLOCK.sql 의 C_HARD_LIST
    ,   'momse12345|203.0.113.7|2026.09 비정상 접속 확인'   -- 설명은 판정에 안 쓰임, 이력용

5. 변경 배포 절차

  1. 어느 상수를 고칠지 4절 표에서 확인하고 해당 .sql 파일만 수정합니다.
  2. 수정한 함수를 CREATE OR REPLACE로 컴파일합니다. 의존 객체(트리거·메뉴 함수)는 Oracle이 자동 재검증합니다.
  3. 컴파일 직후 INVALID 객체가 없는지 확인합니다. 
    SELECT OBJECT_NAME, OBJECT_TYPE, STATUS
FROM   USER_OBJECTS
WHERE  OBJECT_NAME IN ('FN_GET_REAL_IP','FN_GET_CLOUD_IP_LABEL','FN_CHK_CLOUD_IP_YN',
                       'FN_CHK_BLOCK_TARGET_USER_YN','FN_CHK_LOGIN_IP_BLOCK',
                       'FN_GET_MENU_CHK_YN2','TR_TB_WB_LOGIN_HIST_R98');
-- 전부 VALID 여야 함. INVALID 면 ALTER ... COMPILE 후 SHOW ERRORS
  4. 추가한 대상이 실제로 걸리는지 SELECT로 확인합니다. 
    SELECT FN_CHK_LOGIN_IP_BLOCK('momse12345', '203.0.113.7') FROM DUAL;  -- N 기대
SELECT FN_GET_CLOUD_IP_LABEL('203.0.113.200')              FROM DUAL;  -- HostRoyale 기대
SELECT FN_CHK_BLOCK_TARGET_USER_YN('대상계정')               FROM DUAL;  -- Y 기대
  5. 정상 계정이 영향받지 않는지 반대 케이스도 한 번 봅니다 (국내 IP + 일반 계정 → Y).
  6. 배포 후 10~30분 TB_WB_LOGIN_HIST_CHK를 보며 예상 밖 계정이 차단되지 않는지 확인합니다 (6절 첫 쿼리).
전체 최초 설치는 의존 순서 때문에 파일 번호 순(01 → 06)으로 컴파일해야 합니다. ALL_IN_ONE.sql이 그 순서로 합쳐져 있습니다.

6. 정기 점검 쿼리

오늘 차단된 로그인 (트리거)

SELECT A.PROC_DT, A.USER_ID, A.LOGIN_IP, FN_GET_REAL_IP(A.LOGIN_IP) AS REAL_IP,
       FN_GET_CLOUD_IP_LABEL(A.LOGIN_IP) AS CLOUD, A.STAT_CD, A.BRWSR_INFO
FROM   TB_WB_LOGIN_HIST_CHK A
WHERE  A.PROC_FG IN ('I','U')
AND    A.PROC_DT >= TO_CHAR(SYSDATE, 'YYYYMMDD')
ORDER  BY A.PROC_DT DESC;

최근 7일 클라우드 대역에서 온 로그인 시도 (차단 여부 무관)

SELECT A.LOGIN_DATE, A.USER_ID, A.LOGIN_IP,
       FN_GET_CLOUD_IP_LABEL(A.LOGIN_IP)          AS CLOUD,
       FN_CHK_BLOCK_TARGET_USER_YN(A.USER_ID)     AS TARGET_YN,
       FN_CHK_LOGIN_IP_BLOCK(A.USER_ID, A.LOGIN_IP) AS BLOCK_NOW
FROM   TB_WB_LOGIN_HIST A
WHERE  TO_DATE(A.LOGIN_DATE, 'YYYYMMDD') >= TRUNC(SYSDATE) - 7
AND    FN_GET_CLOUD_IP_LABEL(A.LOGIN_IP) IS NOT NULL
ORDER  BY A.LOGIN_DATE DESC, A.LOGIN_DT DESC;
-- TARGET_YN='N' 인데 클라우드 IP 가 반복되면 → C_TARGET_USERS 추가 검토

계정 · IP 별 집계 (감시 후보 찾기)

SELECT A.USER_ID, FN_GET_REAL_IP(A.LOGIN_IP) AS REAL_IP, COUNT(*) CNT,
       MIN(A.LOGIN_DATE) FIRST_DT, MAX(A.LOGIN_DATE) LAST_DT,
       FN_GET_CLOUD_IP_LABEL(A.LOGIN_IP) AS CLOUD
FROM   TB_WB_LOGIN_HIST A
WHERE  TO_DATE(A.LOGIN_DATE, 'YYYYMMDD') >= TRUNC(SYSDATE) - 7
GROUP  BY A.USER_ID, FN_GET_REAL_IP(A.LOGIN_IP), FN_GET_CLOUD_IP_LABEL(A.LOGIN_IP)
HAVING COUNT(*) >= 50
ORDER  BY CNT DESC;

1분 60회 초과로 막힌 메뉴 호출

SELECT A.PROC_DT, A.USER_ID, A.LOGIN_IP
FROM   TB_WB_LOGIN_HIST_CHK A
WHERE  A.PROC_FG = 'C' AND A.BRWSR_INFO LIKE '60%'
AND    A.PROC_DT >= TO_CHAR(SYSDATE - 1, 'YYYYMMDD')
ORDER  BY A.PROC_DT DESC;

현재 감시 대상 전체 명단

SELECT A.USER_ID, 'HQ:' || A.HQ_OFFICE_CD AS SRC FROM TB_HQ_EMPLOYEE A WHERE A.HQ_OFFICE_CD IN ('H0268','DS001')
UNION ALL
SELECT A.USER_ID, 'MS:' || A.STORE_CD     AS SRC FROM TB_MS_EMPLOYEE A WHERE A.STORE_CD     IN ('DS00001','DS00002');
-- 여기에 C_TARGET_USERS 4개(h0268, momse09686, kjsun1117, kjsun11177) 를 더한 것이 전체

이력 테이블 크기 관리

TB_WB_LOGIN_HIST_CHK는 감시 대상 계정의 메뉴 클릭마다 한 행씩 쌓입니다(PROC_FG='C'). 감시 대상이 늘면 증가 속도도 늘어나니 월 1회 정도 30일 이전 데이터를 정리합니다. 1분 카운트에는 최근 1분만 쓰이므로 삭제해도 판정에 영향 없습니다.

DELETE FROM TB_WB_LOGIN_HIST_CHK
WHERE  PROC_FG = 'C' AND PROC_DT < TO_CHAR(SYSDATE - 30, 'YYYYMMDD');
-- I/U(로그인 차단 이력) 는 보안 감사용이니 별도 보관 정책에 따를 것

7. 장애 대응

정상 사용자가 로그인이 안 된다고 한다

  1. 에러 메시지에 Login Blocked: Security Violation,계정,IP,...가 있으면 이 트리거가 막은 것입니다. 없으면 다른 원인.
  2. 왜 걸렸는지 확인: 
    SELECT FN_GET_REAL_IP('에러메시지의 IP')               AS REAL_IP,
       FN_GET_CLOUD_IP_LABEL('에러메시지의 IP')        AS CLOUD,       -- NULL 아니면 대역 차단
       FN_CHK_BLOCK_TARGET_USER_YN('계정')             AS TARGET,      -- Y 면 감시 대상
       FN_CHK_LOGIN_IP_BLOCK('계정', 'IP', 'Y')        AS RESULT
FROM   DUAL;
  3. 대역 오탐(국내 통신사인데 CLOUD가 찍힘)이면 C_CIDR_LIST에서 해당 대역을 빼고 02 재컴파일. 계정 오탐이면 C_TARGET_USERS·본사/매장 코드 확인.
  4. 급하게 특정 계정만 풀어야 하면 C_HARD_LIST/C_TEMP_LIST에서 그 줄을 지우고 04 재컴파일. 재컴파일은 수 초.

메뉴가 열리지 않는다 (USE_YN='N')

원인이 네 가지입니다. 위 쿼리로 RESULT가 N이면 IP 차단, Y인데도 막히면 ① 1분 60회 초과(6절 쿼리), ② 메뉴 함수 STEP 2 URL 규칙, ③ 국외 IP FN_CHK_LOGIN_BLOCK 순으로 봅니다.

전체 차단을 잠시 꺼야 한다

04의 C_BLOCK_HH_FROM/TO를 '25'/'25'처럼 만족 불가능한 값으로 바꾸고 재컴파일하면 STEP 0에서 전부 Y가 되어 판정이 꺼집니다. 다시 켤 때 '00'/'23'. 이 방법은 공용 함수만 건드리므로 트리거를 DISABLE하는 것보다 안전합니다(트리거 DISABLE은 이력 INSERT도 함께 멈춤).

ORA-04068 / 함수 INVALID

상수 목록만 바꿔도 함수 재컴파일이라, 접속 중인 세션에서 첫 호출 시 ORA-04068 existing state of packages has been discarded가 한 번 뜰 수 있습니다. 패키지가 아닌 standalone 함수라 보통 안 나지만, 나면 WAS 재시도로 해소됩니다. INVALID가 남으면 ALTER FUNCTION ... COMPILE 후 SHOW ERRORS.

트리거 에러로 로그인 자체가 전부 실패

공용 함수가 예외를 던지면 트리거 WHEN OTHERS가 -20002로 올려 모든 로그인이 막힙니다. 배포 직후 로그인이 전부 실패하면 즉시 이전 버전 파일로 롤백 컴파일하고 원인(대개 오타·컬럼명)을 찾습니다. 그래서 5절 3~5단계를 건너뛰지 않는 게 중요합니다.

9. 하지 말아야 할 것

  • 국내 통신사 대역을 C_CIDR_LIST에 넣지 않는다. 58.123.54.42(SK브로드밴드 58.120.0.0/13), 182.208.192.55(182.208.0.0/12) 같은 IP는 가입자 회선이라 대역으로 막으면 정상 매장이 통째로 차단된다. 특정 계정만 문제면 C_TEMP_LIST에 쌍으로.
  • 공용 함수 5개에 INSERT/UPDATE를 넣지 않는다. 메뉴 함수가 SELECT 안에서 호출되므로 ORA-14551이 난다. 이력이 필요하면 호출부의 AUTONOMOUS 프로시저에서.
  • 트리거·메뉴 함수 안에 IP 목록을 다시 쓰지 않는다. 그 순간 이번 작업 이전으로 돌아간다. URL 기반 규칙만 06 STEP 2 예외.
  • C_TARGET_HQ_CDS / STORE_CDS에 큰 본사·매장을 넣기 전에 명단 크기를 본다. 감시 대상이 되는 계정은 메뉴 클릭마다 이력 INSERT + 60회 제한 + 특정 화면 2초 딜레이를 받는다. 수백 명이 갑자기 대상이 되면 TB_WB_LOGIN_HIST_CHK가 급증하고 체감 속도가 떨어진다.
  • C_HARD_LIST와 C_TEMP_LIST에 같은 쌍을 두지 않는다. 확정 차단이 먼저 걸려 임시 차단이 의미 없어진다. (현재 momse09686/39.115.138.12가 양쪽에 있는데, 원본 트리거 동작 유지를 위해 남겼다. 임시로 낮추려면 HARD에서 제거.)
  • 요일 조건을 좁힐 때 NLS를 확인한다. TO_CHAR(SYSDATE,'D')는 NLS_TERRITORY에 따라 1이 일요일일 수도 월요일일 수도 있다.
