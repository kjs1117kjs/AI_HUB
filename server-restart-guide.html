LYNK 전체 전원 작업 순서

WAS1에서 NFS 서버를 기동해 /dat1을 공유하고 있습니다. 그래서 WAS1은 다른 WAS·API보다 항상 먼저 올라와 있어야 합니다. WAS1을 내리면 나머지 서버의 공유 디렉터리도 함께 끊깁니다.

전원 ON WAS1 → 나머지 WAS · API → WEB
전원 OFF WEB → API → WAS → WAS1 (마지막)

  1. 서버 전원을 켠다.
  2. root로 로그인한다.

  2. nginx를 종료한다.
  3. 로그에서 종료를 확인한 뒤 전원을 내린다.
systemctl stop nginx

# 종료 확인
cd /usr/local/nginx/logs
tail -f access.log

LYNK WAS 무중단 재기동nginx drain + Redis 세션싱크

담당 김중선
10.81.1.31 WAS1 · nx_tomcat 10.81.0.31 WEB1 · sbpnxpos 10.81.0.32 WEB2 · sbpnxpos

한쪽 WAS를 로드밸런싱에서 빼고(drain) 세션을 넘긴 뒤 작업하는 절차입니다. 서비스를 내리지 않고 WAS를 재기동하거나 배포할 때 사용합니다. 아래 순서대로 진행하며, 세션싱크는 drain·원복 직후 매번 수행합니다.

세션싱크 처리 (WAS1)

아래 단계들에서 반복 호출되는 공통 작업입니다. nx_tomcat 계정으로 WAS1에 접속해 실행합니다.

cd /home/nx_tomcat/redis-session-sync/

# 현재 세션 상태 조회
./redis_check.sh

# 세션 싱크
./redis_sync.sh a
전체 진행 순서
  1. 1
    WEB1 drain 설정

    sbpnxpos@solbi_web1

    cd /usr/local/nginx/conf/conf.d

# 현재 drain 상태 조회
./nginx_drain_check.sh

# drain 설정
sudo ./nginx_drain.sh 1

    설정 후 세션싱크 처리(WAS1)를 진행합니다.

  2. 2
    WEB2 drain 설정

    sbpnxpos@solbi_web2

    cd /usr/local/nginx/conf/conf.d

# 현재 drain 상태 조회
./nginx_drain_check.sh

# drain 설정
sudo ./nginx_drain.sh 1

    설정 후 세션싱크 처리(WAS1)를 진행합니다.

  3. 3
    운영 적용

    대상 WAS · 트래픽이 빠진 상태

    drain된 WAS에 배포·재기동 등 실제 작업을 수행합니다. 재기동은 neo1_startweb / neo2_startweb을 사용합니다.

  4. 4
    WEB1 원복

    sbpnxpos@solbi_web1

    cd /usr/local/nginx/conf/conf.d

# 현재 drain 상태 조회
./nginx_drain_check.sh

# 원복
sudo ./nginx_up.sh 1

    원복 후 세션싱크 처리(WAS1)를 진행합니다.

  5. 5
    WEB2 원복

    sbpnxpos@solbi_web2

    cd /usr/local/nginx/conf/conf.d

# 현재 drain 상태 조회
./nginx_drain_check.sh

# 원복
sudo ./nginx_up.sh 1

    원복 후 세션싱크 처리(WAS1)를 진행합니다. 마지막으로 ./nginx_drain_check.sh로 양쪽 WEB이 모두 정상 상태인지 확인합니다.

drain 상태로 두고 끝내지 않도록 주의하세요. 작업이 끝나면 WEB1·WEB2 양쪽 모두 nginx_up.sh로 원복하고 nginx_drain_check.sh로 확인해야 합니다. 한쪽만 원복하면 트래픽이 계속 한 대에 몰립니다.

진행 순서
  1. 1
    소스 수정사항 확인

    활동 내역에서 이번에 반영될 커밋을 확인합니다.

    http://192.168.0.85:30119/Web/sboffice/activity

  2. 2
    현재 화면 상태 확인

    배포 전 화면을 미리 확인해 두면 반영 여부를 비교할 수 있습니다.

  3. 3
    이전 소스 백업 및 war 삭제

    FTP

    문제 발생 시 되돌릴 수 있도록 기존 sboffice.war를 먼저 백업합니다. 운영은 WAS1·WAS2 양쪽 모두 백업합니다.

    # 개발
/usr/local/tomcat/webapps/sboffice.war

# 운영 WAS1
/usr/local/tomcat-8.0.47-neo1/webapps/sboffice.war

# 운영 WAS2
/usr/local/tomcat-8.0.47-neo2/webapps/sboffice.war

    FTP 삭제가 느리면 서버에서 직접 지웁니다. — rm -rf sboffice sboffice.war

  4. 4
    Jenkins 빌드

    http://192.168.0.170:30009/

    개발/운영 Job을 구분해서 선택한 뒤 Build Now를 실행합니다. 개발은 sbp 계정, 운영은 tomcat 계정 Job입니다.

  5. 5
    war 생성 확인

    FTP

    빌드된 sboffice.war가 대상 webapps에 정상적으로 올라왔는지 확인합니다.

  6. 6
    소스 적용

    Tomcat 중지 → 삭제 → 빌드 → 기동

    개발

    cd /usr/local/tomcat
./shutdown.sh

# webapps 밑 war·폴더 삭제
cd webapps
rm -rf sboffice.war sboffice

# Jenkins에서 Build Now 실행 후
cd /usr/local/tomcat
./startup.sh

# sboffice 폴더가 생성되었는지 확인 후 재기동
./shutdown.sh
./startup.sh

    운영 WAS1

    cd /usr/local/tomcat-8.0.47-neo1
./shutdown.sh

cd webapps
rm -rf sboffice.war sboffice

# Jenkins에서 Build Now 실행 후
cd /usr/local/tomcat-8.0.47-neo1
./startup.sh

# 폴더 생성 확인 후 재기동
./shutdown.sh
./startup.sh

    운영 WAS2

    cd /usr/local/tomcat-8.0.47-neo2
./shutdown.sh

cd webapps
rm -rf sboffice.war sboffice

# Build Now 없이 바로 기동
cd /usr/local/tomcat-8.0.47-neo2
./startup.sh

# 폴더 생성 확인 후 재기동
./shutdown.sh
./startup.sh

    WAS2는 WAS1 빌드 결과를 그대로 사용하므로 Build Now를 다시 실행하지 않습니다.

  7. 7
    화면 확인

    수정사항이 실제로 반영되었는지 확인합니다.

  8. 8
    운영은 한 대씩

    WAS1 완료 후 WAS2 진행

    운영은 WAS1 중지/시작을 먼저 끝내고 화면을 확인한 뒤, WAS2를 같은 방식으로 진행합니다. 두 대를 동시에 내리면 서비스가 끊깁니다.

확인용 명령
# 로그 확인
tail -f /usr/local/tomcat/logs/catalina.out

# 프로세스 확인
ps -ef | grep neo1
ps -ef | grep neo2
ps -ef | grep tomcat

# shutdown.sh로 내려가지 않을 때만 강제 종료
kill -9 PID

삭제 전 백업이 먼저입니다. rm -rf로 지운 뒤에는 되돌릴 수 없으므로, 기존 sboffice.war를 백업했는지 확인하고 진행하세요. 경로를 잘못 입력하면 다른 애플리케이션까지 지워질 수 있으니 webapps 아래에 있는지 확인 후 실행합니다.
